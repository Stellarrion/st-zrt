# st-zrt 0.3 benchmark results

Date: 2026-08-13
Worktree: `release/st-zrt-v0.3`, version 0.3.0
Host: AMD Ryzen 9 7900 (12 cores / 24 threads), NVIDIA GeForce RTX 4090

## Methodology

Primary CPU Criterion suites used release/bench mode and the standard 100-sample configuration.
The tail harness used 10,000 iterations. Auxiliary coverage (`alloc_options`, `concurrency`,
`tensor_access`, and ResNet-50) used Criterion `--quick`; dynamic bucket churn used 1,000 runs.
Numbers are local measurements, not cross-machine guarantees.

The original GPU measurements below were characterization only because `VLLM::EngineCore`
occupied about 16.15 GiB during that run. A later low-contention rerun (no compute workload;
only an idle 33 MiB Nautilus CUDA/graphics context) is reported separately and confirms the same
conclusions. The strict empty-context benchmark guard correctly refused to label that desktop run
fully exclusive, so the results remain local release characterization rather than a bare-device
claim.

The correct device-input graph does not meet the aspirational 1.5x gate.

### Lockless relay_4m

| Lanes | Throughput | p50 | p99 |
|---:|---:|---:|---:|
| 1 | 377 req/s | 2.567 ms | 2.828 ms |
| 2 | 601 req/s | 3.061 ms | 4.246 ms |
| 4 | 622 req/s | 6.200 ms | 8.283 ms |

A diagnostic phase run (also on the shared GPU) attributed one-lane replay approximately to 1.77 us
copy enqueue, 1.246 ms bound-input synchronization, 1.317 ms `RunWithBinding`, and 0.79 us output
synchronization. These legacy phase timings double-count provider work split across two device-wide
barriers. After exact-stream event completion, the optimized one-lane phase run measured about
1.81 us copy enqueue, 0 input-sync, 2.564 ms asynchronous `RunWithBinding`/GPU work, and 0.36 us
final event wait. End-to-end relay latency remained about 2.567 ms: the change removes global
synchronization scope and enables sound overlap, but it does not erase the model's GPU execution.
With four lanes, provider contention dominated and throughput had already plateaued.

## Low-contention GPU rerun

After the unrelated VLLM workload exited, the same GTE-small gate measured **752.5 us** baseline,
**585.7 us** stale host-input graph, and **631.0 us** correct device-input graph medians. The correct
path was **1.19x** faster with `max|diff|=0.0035`; it still did not meet the aspirational 1.5x gate.

The relay_4m 1/2/4-lane sweep measured **377 / 621 / 627 req/s**, with p50 latency
**2.558 / 3.070 / 6.198 ms** and p99 **2.760 / 3.793 / 7.067 ms**. This reproduces the earlier
plateau: two lanes improve throughput, while four primarily increase queueing latency.

Artifacts, including `nvidia-smi` metadata and raw outputs, are under
`target/benchmark-runs/exclusive-20260813/` (intentionally untracked build output).

## Device-output nonblocking submission probe

A follow-up `relay_4m` probe using a pre-resolved bucket, device-resident graph outputs, disabled EP
end-sync, and `cudaEventQuery` measured ORT issue at approximately **4.0–5.1 us p50**. The same
model with host outputs previously kept `RunWithBinding` blocked for about **2.59 ms p50**. This
confirms that output placement—not the sub-microsecond final event wait—is the decisive boundary.
The GPU still takes about **1.33 ms** to complete the device-output workload; nonblocking issue
removes host waiting but does not remove compute. See `bench-c/examples/device_output_no_sync.rs`.
A production reactor must use bounded/adaptive polling or GPU stream waits rather than busy-spin.
`CudaCompletionPoller` now amortizes device validation across a caller-owned batch bitmap.
`OwnedDynamicIoRun::chain_on_stream` now transfers readiness with `cudaStreamWaitEvent` and a
reusable downstream lane event. Its owned chain token retains the ORT lane until the GPU consumer
finishes without creating a CUDA event per request. A no-op device-pointer consumer measured the
combined ORT issue + stream wait + downstream-event record at **4.58 us p50 / 20.74 us p99** in the same low-contention desktop context.

## Optimization priorities suggested by the data

1. **Eliminate or overlap the pre-run bound-input barrier.** Implemented after source-level proof:
   ORT 1.27 IoBinding synchronization calls provider `Sync()` (CUDA: `cudaDeviceSynchronize`), while
   graph replay is enqueued on the configured user stream and honors disabled EP end-sync. ZRT now
   records/reuses a CUDA event after replay and fences that exact stream before output access. The
   optimized phase profile reports input sync 0, event sync about 0.36 us, and preserves correctness.
2. **Pipeline H2D and replay across owned lanes.** Implemented with the existing owned detached-lane
   tokens: each lane is a stable pinned/device buffer pair on its own exact retained stream and event;
   two lanes provide double buffering without rebinding graph pointers. A two-stream CUDA regression
   enqueues both before either completion and completes them out of order.
3. **Keep lane count workload-specific.** Use explicitly benchmarked 1/2/4 lane counts; Celer keeps
   its configured nonzero lane count directly. An earlier unpublished `CudaLaneProfile` façade was
   consolidated into the canonical lane machinery before release. Automatic startup tuning remains intentionally rejected because
   graph capture is device-wide serial and shared-system measurements are not stable enough to save.
4. **Avoid host-visible outputs unless serving needs them.** Implemented
   `ServingLane::with_device_io`: output tensors remain session-owned CUDA allocations and can be
   handed to a downstream GPU consumer after exact-stream event completion. Host slice access is
   rejected. Performance is intentionally not compared until an actual GPU consumer is benchmarked.
5. **Reduce input preparation for large tensors.** Added `ServingLane::fill_inputs` so upstream
   producers write directly into idle lane-owned pinned staging, and migrated Celer's packed adapter
   to fill the complete typed slice array without an intermediate ZRT allocation. The service-level
   packed batch remains because it is owned by scheduler/batching logic.
6. **Preserve the current CPU architecture.** Closed with an explicit stop decision. Cached
   lookup/dispatch is single-digit nanoseconds and prepared lanes are at IoBinding noise. The new
   direct-fill helper is stack-only and counting-allocator tested at zero Rust allocations; no
   further wrapper/map rewrite is justified by the evidence.
7. **Use controlled baselines.** Implemented `scripts/benchmark-zrt.sh`: it records machine/git/
   toolchain/governor/GPU metadata, optionally pins CPUs, saves a named Criterion baseline, and can
   require an empty GPU before CUDA runs. It is non-invasive: it changes no governor and kills no
   process.

## GPU-chain release hardening

The release-candidate script `scripts/compute-sanitizer-zrt.sh` ran the GPU-chain success, callback-error, and panic-after-real-D2D-enqueue tests under Compute Sanitizer. Memcheck, racecheck, initcheck, and synccheck all reported zero errors/hazards. The CUDA suite also passed three consecutive default-parallel runs after every capture test acquired the shared capture lock.

## 10,000-iteration local soak

With `ST_ZRT_DEVICE_OUTPUT_ITERATIONS=10000`, the post-hardening release example completed both 10,000-run loops with changing inputs. Device-output ORT issue measured **4.168 us p50 / 17.262 us p99**; fill through GPU completion measured **1.308 ms p50 / 1.642 ms p99**. GPU-chain issue measured **4.619 us p50 / 19.347 us p99**. These remain low-contention desktop-context measurements, not bare-device claims; an immediately preceding standalone run measured 4.108/16.501 us issue, 1.308/1.593 ms completion, and 4.579/19.186 us chain.

A separate **100-cycle runtime lifecycle soak** repeatedly created, captured, chained, completed, and dropped the device-output graph path. All 100 cycles passed. `scripts/soak-zrt.sh` reproduces both the 10,000-request loops and lifecycle soak; it performs no system mutation.

## Batch completion polling microbenchmark

A 100,000-pass completed-event query probe compared ordinary per-event validation with `CudaCompletionPoller`. One event was noise/slightly slower (**83.5 ns individual vs 85.7 ns batch**); batching is intended for multiple lanes. Results for 2/4/8/16 events were **219.5/339.7/692.3/1404.0 ns individual** versus **147.9/273.8/534.2/1094.4 ns batch**, or **1.48×/1.24×/1.30×/1.28×** faster per polling pass. `bench-c/examples/completion_poller.rs` reproduces this local low-contention characterization.
